# MediaTek MT8196 Chromebooks

CrabEFI runs as the coreboot payload on MT8196 ("rauru") Chromebooks. It has
been tested on Google Navi with Debian, booting through systemd-boot or
directly from Boot Loader Specification entries.

## Supported hardware

| Device | Driver | Notes |
|---|---|---|
| Serial console | 16550 (UART0) | From the coreboot table |
| Display | coreboot framebuffer | Mapped non-cacheable (the display engine does not snoop) |
| Internal keyboard | Chrome EC over SPI (MKBP) | Keymap from the devicetree's `linux,keymap` |
| Touchpad | HID over I2C, precision touchpads | Powers the MT6373 rails and pins it needs |
| TPM | Ti50/Cr50 over I2C | Measured boot (TCG2) continues coreboot's event log |
| Internal storage | UFS | Read-only |
| USB storage | xHCI (primary controller) | Bulk only: no USB keyboards or mice yet; VBUS needs coreboot's "XHCI init done" GPIO |
| UEFI variables | SPI NOR, FMAP region `NVRAM` | Also written at runtime, see below |

## Building

```sh
LOW_DEVICE_GB=2 ./crabefi build --arch aarch64 --machine mt8196 --ui \
    --fit-dtb path/to/mt8196-rauru-navi-sku*.dtb
```

This produces `target/aarch64-unknown-none/release/crabefi` (ELF) and, with
`--fit-dtb`, `crabefi.fit`. The payload is linked at `0x88000000`.
`LOW_DEVICE_GB=2` maps the I/O space below DRAM (2 GiB, including the GPU)
as Device memory; CrabEFI warns at boot if a build maps less.

### FIT payload (recommended)

With `CONFIG_PAYLOAD_FIT`, coreboot selects the devicetree matching the
board/SKU, adds memory, `/chosen/framebuffer` and `/firmware/coreboot`, loads
CrabEFI at its FIT `load` address and passes the devicetree in `x0`. CrabEFI
takes the board description from it: controller addresses, I2C peripherals,
interrupts, pins, supplies and the keymap. This needs coreboot's FIT loader to
honour the kernel image's `load` property.

### ELF payload

Added with `cbfstool add-payload`, CrabEFI gets only the coreboot table, so
it has no board description: the serial console, display and memory work,
but none of the devices above are set up. Use the FIT payload.

### Board GPIOs

The EC switches USB VBUS on only after the payload drives the GPIO coreboot
publishes as "XHCI init done" in its GPIO table (`LB_TAG_GPIO`). coreboot
writes that table only for `CONFIG_CHROMEOS` builds unless it carries the
change that passes board GPIOs to every payload; without the GPIO, USB
devices stay unpowered.

## Variable storage

Variables live in an EDK2 authenticated variable FV in the FMAP region `NVRAM`
(`SMMSTORE` and `RW_NVRAM` are also accepted). It must be sector aligned and
start erased; CrabEFI formats it on first boot. For example, on an 8 MiB flash:

```
FLASH 0x800000 {
	BIOS@0x0 0x800000 {
		BOOTBLOCK 128K
		FMAP@0x20000 0x200
		RW_MRC_CACHE@0x30000 0x10000
		RO_VPD(PRESERVE)@0x40000 0x4000
		COREBOOT(CBFS)@0x44000 0x77c000
		NVRAM@0x7c0000 0x40000
	}
}
```

After ExitBootServices, the runtime image writes non-volatile variables to the
flash itself, so OS changes (`efibootmgr`, `bootctl`) survive a power cut. The
OS must therefore not drive the NOR controller: disable its devicetree node
(`&nor_flash { status = "disabled"; };`). When the region is full or a write
fails, the change is journalled in RAM and applied on the next warm boot.

## Capsule backend enablement

The existing capsule backend can use the same MT8196 NOR controller as the
variable store. Its existing signed RMAP/FMAP handling selects the regions;
variable-store accesses remain bounded to `NVRAM`.

Enable coreboot's `CONFIG_DRIVERS_EFI_FW_INFO` and configure its stable
`DRIVERS_EFI_MAIN_FW_GUID`, firmware version and lowest supported version.
Provide a DER-encoded public signing certificate when building the payload:

```sh
CAPSULE_CERT_PATH=/path/to/capsule-cert.der LOW_DEVICE_GB=2 \
    ./crabefi build --arch aarch64 --machine mt8196 --ui \
    --fit-dtb path/to/mt8196-rauru-navi-sku*.dtb
```

Without this setting, the existing capsule trust store stays empty and
rejects every capsule. Never include the private signing key in the ROM.
Capsule parsing, authentication and RMAP policy are CrabEFI's own.

## Booting Linux

CrabEFI boots EFI applications (systemd-boot, GRUB) and Linux EFI-stub kernels
from BLS entries on the ESP. A `devicetree` line in an entry is installed as the
EFI devicetree table; without it, Linux gets the devicetree coreboot passed
(FIT payloads only). Kernels must be uncompressed `Image` files: gzip-compressed
`vmlinuz` images are not unpacked.

## Memory and DMA

RAM is mapped cacheable. The devicetree marks no device `dma-coherent`: the
xHCI, UFS and I2C DMA masters do not snoop the CPU caches, so CrabEFI gives
devices buffers from a 16 MiB non-cacheable pool. They also reach only the low
4 GiB, so CrabEFI keeps its allocations below 4 GiB; RAM above 4 GiB is left
to the OS.

The serial console is the UART coreboot reports; the devicetree node at its
address (`mediatek,mt6577-uart`) identifies it as a 16550.
